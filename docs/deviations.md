# Deviations from Blender 5.2

Owned by the integrator (ARCHITECTURE §2.1 principle 4, §21.8). Every place where frap
deliberately behaves differently from Blender 5.2.4 is listed here, with its rationale and the
normalisation the golden runner applies on the Blender side (`tools/blender/golden_runner.py::NORMALISE`
mirrors the **Golden** column; WP 1.8 keeps them in sync). Work packages add entries through their
PR description; the integrator merges them here. `--describe` surfaces the operator-level ones as
`frap_note` / `headless`.

Status: M8 W0 (2026-11-22): every §2 row names an M8 WP or M9, the post-M8 backlog (decision log M8W0-3). "Since" is the milestone in which the behaviour exists in code.

## 3. Protocol notes (frap envelope, not Blender behaviour)

- The clipboard (WP 8.3.5): `blender -b` has no system clipboard (`window_manager.clipboard`
  always reads `''`, writes are dropped), so `object.copy_global_transform` /
  `copy_relative_transform` change nothing visible and `object.paste_transform` always fails
  with `Clipboard does not contain a matrix` — frap answers the same (it has no
  `window_manager`). As an envelope extra, the copy operators put the text the add-on would
  have copied (`Matrix((\n    (…),\n …\n))`) in `result.clipboard`, with the hint
  `HEADLESS_CLIPBOARD`.
- `object.align` with `relative_to='OPT_4'` and no active object among the selection
  (WP 8.3.5): the add-on raises `UnboundLocalError` on the first axis, before moving anything,
  and Blender's `RuntimeError` carries the Python traceback with absolute paths of the Blender
  install, the source lines and caret markers, then a `Location:` line naming the calling
  script. frap raises the same `RuntimeError` with a shortened traceback (the two frames, the
  add-on path relative to Blender's version directory, no source excerpt or `Location:`) ending
  in the same `UnboundLocalError: cannot access local variable '…' where it is not associated
  with a value` line.
- `transform.bend` (WP 8.3.5): Blender 5.2.4 registers it without an exec, so a script call
  logs `Invalid operator call 'TRANSFORM_OT_bend'`, changes nothing and returns
  `{'PASS_THROUGH'}`; frap answers `FINISHED` with a WARNING and the hint `BEND_NO_EXEC`
  (a SIMPLE_DEFORM modifier with `deform_method='BEND'` bends instead).
- Response kind `"invalid"`: input that never became a statement (syntax error, invalid UTF-8 on a
  line) gets one `ERROR` response of kind `invalid` (M0). Part of the protocol contract since
  M1 W0 (§13.2; codes `NOT_IMPLEMENTED`, `RNA_NOT_IMPLEMENTED`, `RNA_RUNTIME` are in §13.4).
- The missing parent directories of an export path are created, **as Blender's add-on does**
  (verified: it returns `FINISHED` for a nonexistent directory) — parity, recorded here because it
  surprises reviewers.
- Evaluated meshes (`ob.evaluated_get(dg).data`, `ob.evaluated_get(dg).to_mesh()`) are named
  in responses (`path`, `$coll`, `$ptr`) by the evaluated expression,
  `bpy.data.objects['X'].evaluated_get(bpy.context.evaluated_depsgraph_get()).data…`, which
  reads the same data back; Blender's repr names the original, `bpy.data.meshes['X']…`, whose
  data differs (M3+M4 stabilization, decision log M34S-7).
- A statement that names a function without calling it (`bpy.data.images['X'].save`) reads
  the function object as Python does (`{"$func": …}`, `FINISHED`) and gets the hint
  `FUNC_NOT_CALLED`; unknown enum items carry `detail.did_you_mean` like unknown keys.
- `fcurve.keyframe_points.add(count)` accepts any count up to `INT_MAX` in Blender; frap checks
  the new keys' memory against the `--max-elements` budget first (D-52), so
  `add(2000000000)` answers `LIMIT_EXCEEDED` instead of allocating ~88 GB (WP 6.1).
- Blender's `RuntimeError` messages raised from C reports end with a newline (`"Error: …!\n"`);
  frap's messages never carry trailing whitespace. The golden line comparator ignores it.
